# Stale compile snapshot: options before redesign

Scope: wave 12 root cell `exec-d0ceb51583aa625fee3c4c565ba74201` in run `7d0bd907-1640-49b1-a952-f98005ca6e2d`. This is an options note, not a change to the live host or its freshness rule.

## What happened

The cell took a short machine checkout, then checked its Haskell source off checkout. Compiler preflight waited **83.835 s**; the subsequent check transaction took **0.860 s** (run log 02:21:31.841–02:21:32.740). At the reservation re-checkout, `split_staleness` returned `CompileView` (02:21:32.782). `prepare_cell` immediately used `prepare_cell_single_checkout`; that checkout lasted **165.405 s**, including compiler request `9027a29c3c49901b` with a **130.828 s** response and **124.3 s** prepared projection. The whole cell lasted **292.049 s**. These are nested spans and must not be added. Actor 5 released a nearby checkout at 02:21:32.268, but the old `CompileView` log does not identify which field changed, so it does not establish a cause. Sources: [wave12-slow-calls.md](../wave12-slow-calls.md), [coordination.md](coordination.md), local run JSONL/log at the timestamps above.

The current path is deliberate: `prepare_cell` attempts the split once, then redoes the entire cell under one checkout on any stale reservation, rejection, or install. The comments cite inherited-context parents that keep committing; repeated long GHC attempts may repeatedly go stale. The single-checkout path guarantees an internally consistent compile and eventual progress once admitted, but blocks every other checkout of that machine while compiling. `SessionRegistry` admits waiting checkouts FIFO; it cannot serve that queue during a long hold. Its epoch still fences a removed or replaced machine. See `exomonad/actor/src/resident_workbench.rs` (`prepare_cell`, `reserve_cell_generations`, `split_staleness`, `prepare_cell_single_checkout`) and `tidepool/runtime/src/session/registry.rs` (`checkout_queued`).

`CompileView` means `ActorCompileView::is_current_for` failed. Its owning `SessionCompileView` compares exact session/scope/root, persistent imports, declaration library, visible modules and names, shadowing and staged hiding, and continued liveness of every previously reachable injected module. The generation counter alone is intentionally excluded after a reservation. A cell with a declaration separately checks its candidate declaration module. No evidence from this run justifies relaxing any of those comparisons. The field-level diagnostic added after this run (`56aff5819`, per the coordination audit) should be used on the next occurrence before attributing staleness to a writer or scope.

## Options

| Option | Consistency and progress | Fairness, cancellation, and cost | Required proof |
|---|---|---|---|
| Keep the current locked fallback | Exact fresh view is compiled and installed within one machine checkout. One admitted cell progresses despite a moving parent. | FIFO waiters cannot use the machine during GHC and prepared projection. Cancellation must interrupt the compiler and settle the checkout; the observed hold was 165 s. Avoids a second speculative GHC pass. | Retain current stale reservation/install/rejection tests, timeout and cancellation settlement, and machine epoch fencing. |
| Retry once off checkout after `CompileView` at reservation, then use the existing fallback | A new snapshot and whole-cell check must be followed by the same reservation, rejection, and install revalidations. If stale again, locked fallback still gives progress. Do not reuse the first check's result against the fresh view. | Other actors can run during the retry; the retry may consume another daemon slot and repeat GHC work. This trace's first check itself took under a second, but its preflight waited 84 s; another retry is therefore not predictably cheap in wall time. A busy parent can still force the final locked hold. Cancellation needs one edge covering every attempt and all reserved/leased resources. | Barrier tests for stale at reservation, after item compile, and rejected diagnostic; exactly one retry; second stale falls back; no stale code or diagnostic accepted; generation, declaration, JSON input lease, and cancellation cleanup preserved. Measure queue wait, GHC service, and checkout hold separately. |
| Serialize source writers or reserve a compile view before GHC | A reservation could prevent a relevant ancestor or same-scope writer from changing the imported view until installation, avoiding retries. Existing numeric value-generation reservation only allocates IDs after the check; it does not freeze imports or source. | A view-wide lock held across GHC shifts the long hold from machine checkout to writers and may starve parent progress. A per-scope or dependency-aware reservation needs conflict ordering, fair admission, abort cleanup, actor retirement handling, and treatment of persistent declaration/source publication. More machinery than the demonstrated case supports. | Define the conflict graph and order for parent/child/sibling scopes, declaration and source-layer writes; test deadlock, starvation, cancellation, retirement, and commits that do not affect reachable imports. |
| Versioned source sequencing or optimistic validation | Immutable source versions plus compare-at-install may allow concurrent compilation and make stale outcomes explicit. It still needs a policy when the version changes: retry, reject, or wait. | Requires a new cross-owner protocol among source publication, session imports, GHC artifact identity, and workbench installation. A global sequence number would falsely invalidate unrelated siblings. Memory/artifact retention and version reclamation become additional costs. | Prove one exact authority over version issuance and publication, that old source is never silently committed as current, and that per-scope changes can be distinguished without weakening `is_current_for`. |

## Recommendation

First use the existing field-level stale diagnostic on a comparable case; if it names a legitimately changing field, trial **one bounded off-checkout retry for reservation-stage `CompileView` only**, then retain the present single-checkout fallback. This is the smallest structural candidate that can reduce machine hold without weakening freshness or removing the progress guarantee. Keep the retry local to `prepare_cell`; do not turn `CHEAP_RETRY_ATTEMPTS` into a blanket cell policy or change fragment/display/prepared-install paths. A retry should be chosen on measured compiler service and queue behavior, not the 0.860 s GHC check alone. If the diagnostic instead identifies a spurious invalidation, repair that field's ownership or classification before adding a retry.

Open decisions before implementation: (1) whether a retry's wall-time/daemon-queue budget should cause immediate locked fallback or return a typed busy outcome; (2) whether a repeatedly moving inherited parent merits different policy than a one-off same-scope write; (3) what priority, if any, a fallback gets behind already queued machine checkouts. Returning busy would change the current eventual-progress contract and needs an explicit product decision. No speedup is claimed from this single trace.
