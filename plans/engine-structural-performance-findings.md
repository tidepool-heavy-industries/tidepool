# Structural performance audit findings

Four independent Sol 6.1 source audits completed against Tidepool
`1c510ee583076b0080ec53e23982b2dd6c7ebd19` and pinned harness
`5ab7ee3ee4b288c05b5f73239fec4b99236858a7`, following
[the Astra-designed audit plan](engine-structural-performance-audits.md).
These findings are structural unless a measurement is explicitly identified.
No new runtime test or benchmark was executed by the auditors. The build audit
decoded two retained Buck logs inside bounded scopes; it ran no build.

## Findings by owner

| Codegen retirement | One global descriptor-vector filter per retired program in the same collection batch | Union retiring headers and filter once after existing collection/defer decisions | Nursery deferral, roots/captures, rollback, exact successor site ownership |

| Facade source capture/status | Capture computes then discards digest facts; identity and module inventory reread/hash the snapshot; observation writes and deletes a durable copy | Hand captured evidence to the existing manifest owner; use a fresh read-only inspection path for observation | Ordered roots/shadowing, symlink and complete-read rules, immutable publication snapshots |

The final row is a design hypothesis about removable compiler work. It must be
reviewed with the compiler owner before changing admission. Unchanged run text
alone cannot justify skipping installer compilation: helper sources and compiler
inputs may have changed.

## Evidence and bounds

- The actual debug warmup in `baseline-0092148c64` spent 16.370 s in complete-cell
  compilation, 193.486 ms in native observation and 1.236 s in native display.
  Display added 11 image elections, 3,208 functions and 1,137,315 generated bytes.
  No repeated display completed, and no detailed native category trace was
  retained. This does not show redundant generation; first demand remains a
  plausible explanation. Both selected baseline tests ultimately failed.
- Source capture's core workflow reads/hashes approximately three times its
  Haskell source bytes and writes one full copy, excluding additional headers,
  publication and metadata work. This is a source-derived bound, not timing.
- Replay payload is proportional to the sum of each issued history and schema
  size over rounds. Before compaction, fixed-size additions produce quadratic
  repeated payload growth. References remove payload duplication but still have
  cumulative reference-list growth. Disabling replay is not the proposed fix.
- Frozen runtime production Buck inputs include two `cfg(test)` Rust modules
  totaling 89,333 bytes, plus 28 Haskell and one JSON fixture totaling 11,304
  bytes. Toolchain adds four test Haskell fixtures totaling 972 bytes. The pinned
  Buck Prelude propagates these sources as transitive rustc inputs. The changed
  selector also maps these runtime test edits to six production obligations:
  runtime, testing, MCP, handlers, actor and facade. Rebuild frequency and saved
  time have not been measured.

## Suspicions ruled out or bounded

- Installed typed-tool calls already use retained dispatchers; the existing
  old/new snapshot regression asserts no compiler submission on first/repeated
  calls. The audit inspected that contract, not a fresh executed result.
- Actor tool/source snapshots share Arcs. The manifest-copy finding is at the
  facade and downstream harness boundaries, not those actor snapshot clones.
- `CallScope::compile_count` counts timed wrappers, including native JIT work;
  it is not a GHC request counter. Reconcile with actual daemon request IDs.
- Prepared program payloads/hashes are shared; native registry keys exclude
  machine-local binding identities. Exact inherited demand can reuse installed
  originals. Ordinary static membership is already indexed; parcel export is
  the separate linear path.
- Handle release does not itself trigger collection, and the image registry
  uses weak ownership. Permanent literal retention is not a demonstrated leak
  without an address-lifetime proof and retained-memory evidence.
- Embedded browser transport does not broadcast a whole transcript for every
  provider delta. Snapshots serve connect/resync/lag; history pages are bounded.
- Historical provider-cache measurements do not establish current behavior.
  The existing replay mismatch checker omits `tools_allowed`; before/after
  experiments must compare normalized bodies including `tool_choice`.
- The 94-action metadata build and 91-action runtime bundle use different
  output groups and revisions. Their 21.120 s versus 146.735 s timings do not
  establish a Buck cache regression.
- Development-dependency fanout, several fixed-fixture installation loops and
  low-level test-support separation are already bounded. Missing complete
  fixture dependency evidence legitimately selects the full corpus.

## Integration constraints

Combine facade manifest sharing, harness request preparation and replay changes
into one end-to-end representation design before editing; moving a copy to the
next layer is not a saving. Replay encoding needs an explicit format decision
and exact old-request/repeated-call/compaction tests. Compare normalized provider
input directly, without credentialed inference.

Source observation, native installation metadata and test-input boundaries are
separate implementation parcels. They must not overlap the active compiler
graph/Val-lifetime repairs, persistent recovery snapshots or immutable Prelude
package work. Prefer bounded owner changes and existing failure tests. Record
actual counts and distinguish removed operations from measured latency savings.

## Repair and acceptance checkpoint

The initial findings above describe the audited revision. At integration commit
`611b32438a8c668043c0c593e489cd5d90906ef3`, the following repairs are joined:

- Shared immutable native definition facts, one descriptor filter per retirement
  batch, and indexed static parcel ownership.
- Reused captured source digests, read-only source observation, complete shipped
  source fingerprints, and checking-only reload validation against the current
  published source graph.
- Explicit production/test source ownership, isolated Cargo targets, and bounded
  successful trace copies. Complete benchmark traces publish only after copying
  succeeds; file hashing streams its input.
- One closure/index for exact-context validation and identity, shared compile-view
  metadata, a shared admitted native-owner baseline with private deltas, and direct
  consumption of refreshed injection inventories.
- Live-entry-owned admission queues with epoch fencing, and child machine
  preparation on the existing blocking pool before registration.

The most recent combined Buck check before the final metadata/scheduling/view
batch passed on `4a9971818b7d6a7f9dedbcc06ba8f287355d5c8d`: six production crate
targets, 47 local actions, 23.628 seconds, zero tests executed. Evidence is under
`target/completion-evidence/compiled-cell/buck-joined-reloads/4a9971818b/`.
This is a compile result, not a matched latency comparison. Component evidence
includes 32 metadata tests, six registry tests, two child-preparation tests,
31 initial view/admission tests and nine follow-up tests; these are separate
candidate checks, not a single final acceptance run.

Later source audits found three ownership defects: a borrowed binding exposed as
consumable root custody, portable images failing to admit reused literal addresses
on a fresh machine, and separately passed pending snapshots/compiled images whose
pairing depended on caller convention. Their bounded owner repairs are in flight.
Harness repairs also retain terminal outcome separately from rendered tool output,
so cancellation, failure and error-shaped success survive replay unambiguously.
The immutable package producer, annealing integration and final actor/harness
composition remain delivery gates.

The cold-original acceptance candidate is frozen at
`1b874b9896b93c286a07afd87a9eaac58d9c1c2e`; its matched build passed, with the actual
test still running at this checkpoint. Other focused successes do not close the
engine, M1, M2 or production performance gates. Per the user's completion decision,
finish current repairs and execute joined acceptance and timing measurements before
starting additional speculative optimization work.
