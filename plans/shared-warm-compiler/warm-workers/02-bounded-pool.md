# Wave 2: a bounded shared worker pool

Status: proposed. Supervisor: [warm workers](README.md). Depends on [exact realizations](01-exact-realizations.md) and the parent resource/qualification contract. One worker can serve many closed exact worlds serially; several workers provide bounded parallel capacity. The pool does not assign one process, CPU lease or retained mutable GHC session to each actor.

## Assignment and concrete scope

Retain useful realizations within the existing Haskell/toolchain cache owner and existing daemon resource/process guards. Measure locality before deciding whether to prefer an idle compatible worker when a valid locality reference is available. Inputs are current capacity, configured pool/job/retention budgets, workload, and an optional **physical worker-instance preference** from wave 1. Output is an ordinary fresh admitted transaction/CPU grant on one live slot, with the existing END/deadline/retirement result. Semantic root selection and cache validity remain in toolchain/Haskell owners; the daemon does not inspect artifact graphs or decide which module version an actor means.

Owned files/symbols:

- `tidepool/extract-cmd/src/frontend.rs`: existing `DaemonConfig` and daemon/owned-runner validation consumers; no new CLI option is required for the core wave. `lib.rs` matched helper arguments change only if the optional follow-up is separately authorized.
- `daemon.rs`: `WorkerSizing`, `validate_worker_footprint`, `ResourceAdmission::acquire_with_capacity`, `serve_workers`, `service_transaction`, `Worker::spawn_in_slot`/replacement.
- `resources.rs`: host and ancestor cgroup observation, typed refusal.
- `request.rs`/`endpoint.rs`: physical locality field and worker-instance response if wave 1 did not already land them; coordinate one protocol owner.
- `bridge/haskell/src/Tidepool/GhcPipeline.hs`: bounded completed realization retention, exact holds and interpreter transition; `ExactScope.hs` original-input retention accounting. Toolchain owns semantic policy configuration and descriptive observations.

Do not add a second launcher, scheduler daemon, per-actor process map, global cache hash registry or shared cross-daemon reservation service in this wave.

## Chosen resource and locality policy

Keep the existing admission policy and defaults for the core wave: the present min(21 GiB, available minus headroom) budget and up to three admitted workers are enough to prove many exact worlds sharing a bounded pool. No budget override, CLI/schema fanout or larger process count is a prerequisite for bounded realization retention or the frontend experiment. Preserve actual host/ancestor capacity checks and typed refusal.

Worker count, per-request foreground/preparation job width, process RSS rotation and semantic realization retention are separate controls. Document purpose and units. Keep the historical 7 GiB warm floor until new representative peak/retention measurements justify replacing it. A lower RSS ceiling must not bypass warm-footprint admission. Startup failure remains a typed resource refusal before spawning/publishing the service. Live admission includes idle retained workers and prospective growth, not just the currently active one. Runtime current capacity can still refuse work after a valid startup configuration. The existing process admission budget is prospective capacity policy, not a hard sum of all retained Haskell heap bytes or an in-flight peak bound. Keep actual process/cgroup guards and the narrow finite cache-retention policy below.

Use the wave-1 physical worker-instance reference as a **soft preference** only. Prefer that worker when it is live, idle and eligible for the workload, otherwise use the existing reserved-foreground/idle-spill admission. Never wait on a busy preferred worker while an otherwise eligible idle worker is available merely to keep locality. Never allow preparation to occupy reserved foreground capacity. An admitted queued job is not an actor's permanent assignment. Keep bounded queue/backpressure and no affinity-specific pending list; report existing queue/head-of-line behavior rather than claiming a fairness redesign. A semantic miss on the chosen worker goes through confirmed source-free acquisition, not another arbitrary scheduling retry.

A worker instance changes every spawn/replacement even within the same daemon epoch/slot. Remove locality hints for retired instances. One active outer transaction per worker remains; CPU/resources stay held through cleanup/owned rotation, then release. Suspended actors retain only logical input roots and optional best-effort realization references. Finishing an actor request does not terminate the process or evict common packages.

## Retention and interpreter lifecycle

Haskell/toolchain retain completed exact nodes under the existing CompilerUniverse. Count unique owned rows, decoded owners and selected roots separately from references. Eviction removes only inactive acceleration after transaction holds settle. Shared nodes remain while another realization uses them. Live scopes retain their own immutable input owners through END; host roots retain portable inputs independently after END. An evicted handle returns NeedsAcquisition before source acceptance; missing current root authority or corrupt storage is a refusal, not a miss.

Do not retain raw HscEnv/TcGblEnv chains per actor. A realization is a selected immutable graph and specific lazy package/knot owners. Audit which decoded fact pins an arena extent, directory, entire old HPT or graph. Bound backing bytes/decoded residency as well as entry count; a small selected slice can retain a large arena. The owned-input retention wave supplies independent byte leases and fresh output-root policy.

Keep finite entry/backing-retention accounting in the existing Haskell/toolchain cache owner; do not create a global memory ledger or require exact GHC heap accounting before progress. Track the row/arena/directory extents and decoded owners this cache actually retains, distinguish shared references and active non-evictable holds, and report unknown memory explicitly. Choose and independently review a finite cache policy with the qualification owner using observed retention; conservative estimates and process residency complement it. Before retaining another inactive realization, evict eligible cache entries when that policy requires it. If backing remains unbounded or its release cannot be established, decline optional retention or use confirmed idle-worker retirement rather than claiming that dropping a logical root released the heap. Resource refusal must remain source-free and cannot invalidate already accepted source work.

Audit and bound the actual strong owners in `CompilerUniverse::universeSourceVersions`, `universeOriginalVersions`, `universeRecovery`/`CompilerRecoveryCaches`, `universeOriginalInputs` and retained completed environments, not just the new realization map. A dropped root does not release objects still held there. Remove obsolete acceleration entries through their owning eviction functions; never revoke live leases or source authority. Verify release after last inactive owner through owner counters plus controlled GC/residency observations, and account for lazily retained old HPT knots. If these existing stores cannot release the required backing independently, bounded idle-worker retirement is the explicit fallback; retain quarantine through confirmed process/interpreter cleanup. A realization-only LRU is insufficient acceptance.

Preserve `activateCompilerInterpreter` as the one executable owner. Keep compatible inactive code; a same-owner replacement invalidates its reverse closure and incompatible native/object code retires external iserv. Metadata realization references can survive only under their metadata owner contract; old linkables/ForeignHValues are epoch-fenced. Do not infer executable compatibility from canonical interface/ABI equality or silently rebind historical native edges. Profiles requiring host-plugin isolation use an explicit unsupported/refused capability or a separately admitted worker partition, not unreviewed concurrent global state.

Current count/RSS rotation occurs after settled transaction cleanup; default request count is 1024. Keep that contract while instrumenting whether it discards valuable realizations too early. RSS rotation is not a hard in-flight memory limit. Cancel/deadline/crash cleanup must settle/reap the exact worker and its descendants before slot scratch is reused. Unconfirmed child retirement keeps existing quarantine/resource ownership; do not advertise the slot free because its PID disappeared.

## Implementation waves within this assignment

1. Integrate Haskell/toolchain completed-realization retention/eviction with narrow finite cache accounting, transaction holds and existing input ownership. Preserve current admission defaults and process counts. Prove that eviction reaches existing global version/recovery/input strong owners; exercise confirmed idle-worker retirement when it cannot. Record exact root/instance lifetime through normal END, failure and replacement. Keep cache policy out of extract-cmd.
2. Run small joined A/B/A, many-suspended/few-active and worker-replacement histories on 1/2/3 admitted slots. Compile affected consumers early, then join the exact-candidate changes and update nearest worker/resource guidance. This is the core completion path.
3. Consume the stable worker-instance issuer and measure current locality misses/acquisition/epoch costs. Add the specified soft idle-worker preference only after the parent records a measured benefit and its scheduling decision; otherwise retain current routing and record that result. Treat the reference as physical locality only. Prove stale hint, missing worker and busy-preference paths do not bypass workload or resource admission. Unmeasured affinity is not a prerequisite for bounded retention.
4. Consider the optional capacity follow-up below only if current policy demonstrably blocks useful measured parallelism. Core wave completion and the next frontend experiment do not wait for it.

## Frontdoor and refusal controls

Extend maintained ResourceAdmission stateful/property histories with independent arithmetic for aggregate CPU, preparation reservation, worker counts, current capacity, queued/released grants and cancellation. Enter through daemon configuration/admission in process controls; a pure sizing helper alone does not prove correct child lifetime.

Core controls cover existing invalid count/capacity settings and actual ancestor/host headroom; malformed/unreadable installed cgroup controls; idle resident RSS counted; finite cache admission/eviction with shared backing, active holds and unreleased old global owners; warm-floor rejection; no preparation capacity with one worker; soft hint to busy/dead/replaced worker; concurrent foreground and preparation; request timeout; disconnect before/after source acceptance; cancelled transaction with descendants/uncertain END; busy scratch retained; ordinary versus persistent daemon rotation. Include one worker serving two conflicting exact worlds and a second worker serving compatible shared roots; count interpreter epoch changes separately from metadata misses.

Run existing named daemon controls such as `preparation_reserves_stable_warm_foreground_slot_and_aggregate_cpus`, `failed_acceptance_releases_slot_and_grant_without_worker_execution`, `one_shot_response_commits_after_cleanup_and_only_early_disconnect_replaces_worker`, and hung-worker deadline controls through the counted `just test-lib tidepool-extract-cmd` runner, verifying exact names/counts at implementation revision. Compile/run changed resource/frontend callers and actual native worker lifecycle histories. Fake workers test transport scheduling; they do not prove GHC lazy-world safety or memory peaks.

The selection handoff's independent root/edge controls remain mandatory after routing/eviction. Optional retained implementations stay inactive; a historical required child is not rebound during cold rehydration, spill or interpreter replacement. Reload generation retirement cannot authorize new work from old handles; accepted old work keeps historical dependencies until its existing settlement completes.

## Measurement and stop rules

Separate process slots, actor count, active compiler operations, per-request jobs and dormant retained worlds. Use 1/2/3 slots and identical histories for the core qualification. A larger process/swap sweep belongs only to the separately approved follow-up below. An earlier compiler-process sample on the 125 GiB host had an enclosing 104 GiB memory/2 GiB swap limit; later plan-author scope observations differed. These are scope-specific planning snapshots, not guaranteed future worker limits. Inspect the actual daemon/worker/descendant cgroup chain for each run; other activity and process descendants share whatever limits are then observed. Swap acceptance by the user permits investigation, not treating host swap as effective cgroup capacity or equating cold pages with hot latency.

Record queue/service/END/rotation intervals, wall and CPU, matched source work, realization locality hit/miss/acquisition counts, interpreter epochs, encoded/decoded/backing bytes, process-tree RSS/PSS/SwapPss and major faults, current/high/max/pressure, allocation/GC and scratch growth. Keep first boot, cold hydration, warm query/cell and swap reactivation separate. Name retained processes and surviving cache owners when reporting. A worker RSS drop after swapping does not prove total retained state was released.

Qualification sets explicit pressure/latency/disk stop thresholds before expanding the sweep and observes terminal outcomes afterward. A refusal is retained evidence, not permission to bypass admission. No broad cache clearing, killall or output deletion is a recovery step. With many suspended actors require zero persistent CPU grants/transactions and memory growth attributable to unique facts/backing owners. With hot incompatible actors measure whether affinity saves epoch resets rather than assuming metadata misses are their cause.

## Optional post-measurement capacity follow-up

Only if the existing admission policy blocks demonstrated useful parallelism may the supervisor authorize a separate budget-override change and larger pool/swap sweep. A proposed `--memory-budget-mb` option would extend the existing daemon/owned-runner configuration owner, preserve the current default, validate an explicit request against actual host/ancestor headroom and the warm floor, report requested/effective limits, and refuse impossible settings. Its CLI/schema/caller migration, zero/overflow/malformed-value and capacity controls belong to that follow-up, not the core wave.

The earlier 8–12-process/64–84 GiB range is only an experimental envelope. Qualification must first lock useful-benefit, pressure/latency/disk stop criteria and admission, then inspect actual descendants and compare controlled results. No operational expansion is authorized by this plan itself.

## Deletion and integration gate

Preserve the existing budget/configuration path in the core wave. Remove obsolete per-slot/actor affinity side maps if the final routing metadata replaces them. Delete duplicate resource accounting and tests that only assert old arbitrary constants; retain meaningful warm-floor, headroom and cancellation controls. If the optional capacity follow-up is authorized, update launcher/CLI docs and every supported construction of DaemonConfig together; otherwise leave that surface unchanged.

Independent review reads admission, accepted-connection lifetime, retirement/quarantine, cache holds and Haskell interpreter transitions across the cumulative wave. Fold only after changed owners and downstream test callers compile, counted controls execute, and one real worker history survives replacement with exact root/edge behavior. Link qualification's joined history and performance reports; do not report “pool accepted” from a startup sizing test or idle RSS sample. The parent supervisor owns any deployed process/budget change.
