# Structural performance audits

Four independent Sol 6.1 audits, designed with Astra, complement the current
compiler repairs and engine/harness acceptance work. Their objective is to remove
unnecessary work, not to add caches around it. Initial audits are read-only.

## Common baseline and method

Freeze Tidepool source at `1c510ee583076b0080ec53e23982b2dd6c7ebd19` and its
actual harness pin `5ab7ee3ee4b288c05b5f73239fec4b99236858a7`. Use isolated
recorded checkouts or `git show`. The shared harness checkout has since advanced;
label any comparison with it separately. Preserve the root checkout's unrelated
`flake.nix` WIP and `test-source-boot/`.

Read repository/subsystem contributor rules, the glossary, the RSI workflow
method, and the compiled-cell delivery and resident-performance plans. Trace a
concrete production workflow: intended result, steps, participants, information
already available, owning authority, dependencies, continuation and cleanup.
Follow suspicious helpers to real consumers before proposing changes.

For each finding, distinguish measured cost, structural count/bound, hypothesis
and disproved suspicion. Identify an operation that can disappear and its
frequency, bytes and scaling variable. Compare deletion, ownership transfer,
narrower admission and batching before caching. State exactly which checks must
remain fresh and which immutable evidence can be reused.

Consider latency/throughput, allocation/retained memory, generated code, disk,
build/test cost, dependency fanout, control-flow/API simplicity, correctness,
failure isolation and maintenance. At most three ranked repair candidates per
reviewer, plus an explicit list of disproved suspicions.

Do not implement repairs or spawn further agents during the audit. Hand overlaps
to the existing owners: compiler lexical/interface/native graph semantics,
persistent recovery snapshots, precompiled Prelude/catalog, frozen workspace
source roots, warm/cancellation measurement fixtures, and startup/actor gates.

Use retained evidence first. Do not wait for a compiler slot. If evidence cannot
resolve a material question, propose one bounded experiment: exact command,
binary/pair, expected executed count, duration/resources and discriminating
outcomes. Root coordinates admission with existing work; no global shared
compiler-slot restriction is introduced. No broad batteries, live providers,
cache clearing, daemon restarts or alternate launchers. Buck remains local-only
inside the admitted slice. Mutating cache probes require an isolated provisioned
checkout, never the shared active checkout.

## 1. Native installation, display and retained memory

Own admitted item -> native demand/install -> display -> capture retention ->
last-reader release. Start in runtime `session/prepared.rs`, codegen prepared
program compilation/image registry/binding membership, heap/root owners, and
the production `resident_workbench` consumer.

Compare first evaluation/display, repeated evaluation of admitted products,
independent private installations sharing code, and capture survival followed
by final release. Classify work per item, installation, demanded original and
machine. Inspect repeated fact extraction, demand expansion, image keys,
installation tables, static-region searches and cleanup traversal. Preserve
fresh mutable CAF state and exact live ownership.

Retained debug warmup: compile cell 16.370 s, native observe 193 ms, native display
1.236 s. During display, programs/image elections rise from 1 to 12, functions
108 to 3,316, generated bytes 21,367 to 1,158,682. Determine whether that is
necessary first use, repeated work or unknown; do not assume redundancy.
Use existing protected-scale/prepared-install counters and CODEGEN_DETAIL /
MEMORY_DETAIL traces, respecting overlapping metric scopes. An optional fixed
prepared-program installation test should avoid fresh Haskell compilation.

## 2. AgentSpec, tool preparation and compiler request topology

Own installation/reload orchestration through immutable prepared-item handoff
and request-pinned tool snapshot creation. Read actor AgentSpec/reload/after-tool
owners, facade installation consumers, hosted dispatch and AgentSpec tests.

Trace initial installation, first/repeated call, same-surface implementation
reload, an old in-flight request after reload, and helper-source changes. Count
compiler submissions, inventory walks, schema construction/validation,
dispatcher preparation, after-tool work and tool snapshot creation. Distinguish
once-per-installation, reload, provider request and invocation responsibilities.

Use call_timing and daemon JSONL. Timed wrapper counts need reconciliation with
actual worker request IDs/PIDs/epochs. The existing
`issued_tool_snapshot_keeps_old_handler_after_spec_reload` test asserts zero
compiler work for first and repeated calls; audit surrounding preparation rather
than assume that contract is broken. Skipped reloads must account for helper
sources, producer/packages and source-layer authority, not just entry text.

## 3. Harness history, provider requests and streaming

Own request-pinned snapshot -> Store/history -> normalized provider request ->
transport stream -> browser reconstruction, using the pinned harness revision.
Read engine/history/store/transport/compaction/checkpoint/server/WebSocket owners
and Tidepool's real embedding adapter.

Map representations and lifetimes for a tool round, continuation, compaction,
reconnect with late output, and repeated provider call IDs across requests.
Inspect full-history cloning/decoding, repeated schema encoding, whole-state
broadcasts, event amplification and excess retained buffers. Separate required
stateless provider input from avoidable internal reconstruction.

Inventory actual captures before claiming request-cache evidence. Existing
bounded redacted tracing, replay transport, WebSocket fixtures and
`docs/item2-trace-plan.md` are the first tools. An optional offline transcript
at two history sizes plus reconnect can compare Store/decode/serialization and
browser bytes without inference. Preserve normalized request semantics, original
operation identity, compaction lineage, ordering and no effect replay. Provider
cache/token savings require actual requests and usage evidence.

## 4. Build/test fanout and immutable fixtures

Own source edit -> smallest valid build/test obligation. Read changed-target and
fixture dependency selection, battery/fixture runners, Cargo/Cabal manifests,
Buck generation/cache gates and embedded artifact producers.

Trace runtime implementation, Haskell helper, test-fixture and shared-schema
edits. Inspect unnecessary fixed-fixture recompilation, heavy low-level test
dependencies, generated-input breadth and action granularity. Preserve complete
index fallback, structural corpus requirements and crash/signal isolation.

The 94-action, 21.120 s library metadata build and earlier 91-action, 146.735 s
runtime bundle are different output groups/revisions: rmeta/check versus rlib
and linking. They do not establish a cache regression. Inspect retained Buck
events and exact action identity before an optional identical-target/profile
no-op repeat. Only an unexplained action justifies an invalidation experiment.

## Evidence and result format

Start with the retained directory
`/tmp/tidepool-compiled-cell-performance/target/completion-evidence/resident-performance/`:
`baseline-0092148c64/{manifest.json,baseline.log,durable-partial-report.json}`,
its battery compiler JSONL/logs, `cold-static-work-attribution.json` and
`v4-v5-foundation-storage.json`. Root Buck evidence is under
`target/completion-evidence/compiled-cell/`.

The baseline ultimately failed both selected tests. Its 119.841 s foundation
and 18.773 s warmup are diagnostic debug measurements. The same-worker snapshot
size change from 12,663,202 to 388,062 bytes is actual storage evidence, not a
latency improvement or accepted production benchmark.

Each proposed change must report: owner/production consumer; exact source and
artifact identity; workflow and failure/cleanup; claim category; source or
executed evidence; avoidable work and scaling; required authority checks;
alternatives; smallest change/affected consumers; correctness/failure tests;
cost effects; one optional experiment; overlap owner, confidence and unknowns.

Root combines the four workflow maps before authorizing repairs, checking that
costs disappear rather than merely move across component boundaries.
